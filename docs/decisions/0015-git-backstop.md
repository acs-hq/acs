# 0015 — Git backstop (WP2.4)

Date: 2026-10-30. Status: accepted (WP2.4), pending orchestrator review.

## Context

The hook pipeline (0012) only sees what an agent does through a harness tool call. Plain `git`
commands, a person's own commits, and an agent that goes around its tools are not covered. WP2.4
adds the git-side backstop: an installer for `pre-commit`, `prepare-commit-msg` and `pre-push` hooks
that chain with whatever is already there, the `acs git-hook` command they call, and the trailer
code of SPEC section 7. Decisions 0011 and 0012 fixed the pieces it builds on (pending-commit
markers, seats, attributions, the claims snapshot).

## Decision

### Installer (`acs_git::hooks`)

- **API:** `locate(&RepoLayout) -> HooksLocation`, `install(&RepoLayout) -> InstallReport`,
  `uninstall(&RepoLayout) -> Vec<HookRemoval>`, `status(&RepoLayout) -> HooksStatus` (`healthy()`),
  all returning `HooksError` (`Io`, `Disabled`, `Conflict`). `HOOK_NAMES` lists the three hooks.
  WP2.5's `acs init` calls `install`, `acs doctor` calls `status` and `install` again to repair.
- **Where hooks live** (researched 2026-10-30):
  - Default: `core.hooksPath` unset means `<common git dir>/hooks`. Linked worktrees share it, so
    one install covers all of them (tested with `git worktree add`).
  - `core.hooksPath` is read with `git config --type=path --get` (so `~` expands; retried without
    `--type` for git older than 2.18). Absolute paths are used as they are; relative paths are
    relative to the work tree root, which is where git runs hooks (git-config docs). A relative path
    therefore resolves per worktree; the report says `shared_by_worktrees: false`. `/dev/null` and
    `NUL` mean the person turned hooks off: `HooksError::Disabled`, nothing is touched.
  - **husky 9** (`index.js` of husky, read on 2026-10-30): `husky` sets `core.hooksPath=.husky/_`
    (or `<dir>/_`), and writes into `.husky/_/` a `.gitignore` containing `*`, the runner `h`, a
    deprecated `husky.sh`, and one stub per hook (14 names) with mode 0755 and the content
    `#!/usr/bin/env sh` / `. "$(dirname "$0")/h"`. The runner runs the user's script
    `.husky/<hook>` (parent of the stub directory) with `sh -e "$s" "$@"` and exits with its
    status; it skips silently when the user script is missing and honours `HUSKY=0`. Everything in
    `.husky/_` is regenerated and git-ignored, so **ACS edits the user scripts in `.husky/`**
    (committed, shared with the team) and never the stubs. Detected as: hooks directory named `_`
    holding `h` (or `husky.sh`).
  - **husky 5 to 8**: `core.hooksPath=.husky`, scripts there start with `#!/usr/bin/env sh` and
    `. "$(dirname -- "$0")/_/husky.sh"`; detected by `<hooksPath>/_/husky.sh`. The block goes
    after the `husky.sh` line (looked for in the first four lines), so `HUSKY=0` still disables ACS.
  - **husky 4** wrote scripts into `.git/hooks`: the default layout; `npm install` rewrites them
    and drops the block, which `status` shows and `install` repairs.
  - **pre-commit framework** (pre-commit.com, `hook-tmpl`): `pre-commit install` writes a bash
    script into `.git/hooks/<hook>` (header `File generated by pre-commit: https://pre-commit.com`)
    that execs `pre-commit hook-impl ...`, and moves a pre-existing hook to `<hook>.legacy`, which it
    runs itself. It refuses to install when `core.hooksPath` is set. ACS treats its script like any
    shell script (block inserted after the shebang, before the final `exec`), recognises it for
    `status` (`Framework::PreCommit`), and it survives until `pre-commit install` rewrites the file.
    **Verification gap:** the template body was summarised by a fetch tool, not read verbatim; the
    `ID:` line in the test fixture is from memory. The behaviour relied on (a bash script with a
    header comment that ends in `exec`) is what the docs state.
- **Chaining, never overwriting.** Three cases, picked per hook file:
  1. no file: a new executable `#!/bin/sh` script holding the ACS block;
  2. a text file that is a shell script (shebang `sh`, `bash`, `dash`, `ash`, `zsh`, `ksh`, `mksh`,
     `busybox`, directly or through `env`; or no shebang; always for husky 9, which runs scripts
     with `sh`): the block is inserted after the shebang between `# >>> acs git-hook <name> v1 ...`
     and `# <<< acs git-hook <name> <<<`. Nothing else is touched, so `uninstall` restores the file
     byte for byte (tested), and the file keeps its mode (a non-executable hook stays so and is
     reported `active: false`; ACS does not enable what someone disabled);
  3. anything else (Python, Node, a binary, a symlink): the original is **renamed** to
     `<hook>.acs-orig` and a wrapper (block, then `exec "$(dirname "$0")/<hook>.acs-orig" "$@"`)
     takes its place; `uninstall` renames it back. An existing `.acs-orig` is a `Conflict`.
  Why in-place insertion rather than always wrapping: wrapping renames files that are often
  tracked (husky, `.githooks`), and tools like `pre-commit install` expect their own name.
- **Idempotent and self-repairing.** A current block is left alone; an outdated version is replaced
  (`Action::Updated`); `status` reports `installed`, `up_to_date`, `chained`, `active`.
- **The block** is POSIX `sh` (no bashisms; `command -v`, `mktemp`, `exec <file`), LF line endings,
  written with Git for Windows' sh in mind. It runs `acs git-hook <name> "$@"` and exits with its
  status if non-zero; the original runs after it.
  **If `acs` is not on `PATH` it prints one line on stderr and lets git proceed** (the backstop
  fails open; the gate is the hook pipeline).
  `pre-push` reads its refs from stdin, which the original hook may need as well: the block copies
  stdin to a temporary file, feeds that to `acs`, then reopens stdin on it for the rest of the
  script (tested with a second hook reading stdin).
- **Global `core.hooksPath`** (e.g. `~/.githooks` for every repository): ACS installs there, as the
  configuration says that is where hooks live. In a repository without `.acs/policy` the hooks do
  nothing and say nothing (see below), so other repositories are not disturbed.

### `acs git-hook` (`commands/git_hook.rs`)

- **Fail open everywhere.** Any error reading state, a panic, an unknown hook name, wrong
  arguments (clap errors for `git-hook` exit 0, unlike `hook` which exits 1: here any non-zero
  rejects a commit) allow the operation, with `acs: warning: ...` on stderr. Only a clear violation
  exits 1.
- **No `.acs/policy` directory in the work tree: allow silently.** The brief asked for a warning
  when the repository has no ACS policy; a warning on every commit of every repository would make
  a global hooks directory unusable and teaches people to ignore the output. The warning is kept
  for the case that matters: an ACS repository whose state is unavailable (`ACS_HOME` unusable,
  database error). `acs init` writes `.acs/policy`, so installed hooks always find it.
- **Who is an agent.** `pre-commit` and `prepare-commit-msg`: a pending-commit marker for this work
  tree younger than ten minutes (`hook::markers::read_commit_marker`), as in 0011. `pre-push`: a
  pending-**push** marker (below) or the harness environment: `CLAUDECODE=1` (set for Claude Code's
  Bash tool and inherited by git and its hooks, docs/adapters/claude-code.md section 7) or
  `ANTIGRAVITY_CONVERSATION_ID` set (reported for Antigravity hook processes, **unverified**,
  docs/adapters/antigravity.md). Environment variables are not used for commits: a marker is exact
  about which session it is, and the trailer needs that.
- **Push markers.** The pre-tool pipeline now also writes `pending/push/<key>.json` (same content
  and key as the commit marker, `markers::write_push_marker`) when an allowed shell event contains a
  `git push` (any `GitInvocation` with subcommand `push`; one `pushes()` helper and one call in
  `leave_markers`). Separate files so a commit does not consume a push. `pre-push` consumes it
  whatever the push is, so a person's push right after an agent's is not taken for an agent's.
  `read_/take_commit_marker`, `read_/take_push_marker` were added to `markers.rs`.
- **pre-commit.** Staged paths come from `git diff --cached --raw -z --no-renames` (a rename is the
  old path as a deletion plus the new path), with the `GIT_*` environment git set kept (with
  `git commit -a` or `git commit <paths>` git runs hooks on a temporary `GIT_INDEX_FILE`; the
  `acs_git::repo` helpers strip it, so `hooks::query` has its own; tested with `commit -a`).
  - Agent commit: reject staged paths matching `sealed_match` or a sealed zone, and paths covered
    by a live claim of **any other seat** (local; remote when the view is not stale), on the
    default target branch (all seats use it, 0012). A claim on any scope in the file counts, symbol
    claims included (the hook cannot tell which symbols changed).
  - Human commit: sealed paths are not checked (sealing is for agents); reject paths with a live
    remote claim, or a local claim of a seat whose `worktree` differs from this one, or whose seat
    cannot be found. Claims of seats in this work tree pass (agent edits, human commits).
  - `acs off` (`gate_off`) skips the claim check, as the engine does; sealed still holds.
  - Remote claims with a stale view are skipped with a warning, only when a remote exists and a sync
    was attempted (same rule as `run_gate`).
  - Messages name each path (at most eight, then "and N more"), the holder's pilot, harness, when
    the claim was taken and when the holder was last active, then what to do. For agents: unstage,
    wait, coordinate through the pilot; **they are not pointed at `--no-verify`**. For people:
    wait, coordinate, or `git commit --no-verify` as the explicit override.
  - A rejected agent commit **removes its marker**, so the next commit (a person's) is not mistaken
    for it. A marker left by an agent commit that a later hook of the user rejects stays until it
    expires (ten minutes): a person's commit in that window is judged as an agent's (known gap).
- **prepare-commit-msg `<file> [source] [sha]`.**
  - A fresh commit marker: add `ACS-Session: <marker.session_id>` and consume the marker. For every
    source, merges and amends included.
  - Otherwise (a person): one trailer per session whose recorded changes are in the staged diff,
    **excluded** for source `merge` and `squash`, and while a rebase, cherry-pick or revert is in
    progress (`rebase-merge`, `rebase-apply`, `CHERRY_PICK_HEAD`, `REVERT_HEAD` in the git dir):
    the staged changes are then other commits' work, not a session's.
  - **Attribution rule.** For each staged path (at most 2,000), the rows of `attributions` of
    sessions whose seat's worktree is this one and whose harness is not `human`; the newest row of
    each seat counts. It covers the path when its `post_hash` equals the SHA-256 of the staged blob
    (a deletion matches `post_hash = None`); or, when the staged content differs (a person edited
    on top, a clean filter changed line endings), when the attribution is not older, to the second,
    than the last commit that touched the path (`git log -1 --format=%ct HEAD -- path`; none means
    it counts). `>=` rather than `>`: commit time has one-second resolution and a missing trailer is
    worse than a repeated one; the rare cost is a repeated trailer when a session's change and two
    commits to the same path fall in one second.
  - `--amend` and `-c/-C` (source `commit`): the staged diff is what is new, existing trailers stay,
    duplicates are not added.
  - Trailers are added **without spawning git**, by `acs_git::trailers`, a re-implementation of
    `git interpret-trailers` rules (last paragraph, never the subject, all-trailers or recognised
    prefix with a quarter of lines, indented continuations, comment lines and the scissors tail
    ignored, trailers go before the editor's trailing comments, `core.commentChar` read, CRLF kept,
    no duplicates by token (ignoring case) and value). `tests/trailers.rs` compares it with the real
    `git interpret-trailers --if-exists addIfDifferent` on 13 messages. Difference: a message
    without a final newline gets a blank line before the trailer (git joins it to the subject).
  - An empty message (`git commit` opening the editor) gets two blank lines, then the trailer,
    keeping the first line free for the subject. If the person saves without a subject, git does not
    see an empty message because of the trailer (same as `git commit --trailer`).
  - Not UTF-8 message files are left alone.
- **pre-push `<remote> <url>`.** For an agent push, reject a ref update when the remote ref is
  `refs/heads/<branch>` with `PolicyView::is_protected_branch(branch)` and it is a deletion (local
  sha all zeros) or a non-fast-forward (the remote sha is not an ancestor of the local sha by
  `git merge-base --is-ancestor`; an unknown object counts as not an ancestor, since git would
  refuse a real fast-forward whose base is missing). Tags and other refs are not checked. New
  branches are not force pushes. `acs off` allows.

### Tests

Real `git` and the real `acs` binary (found through `CARGO_BIN_EXE_acs`, put first on `PATH`),
driven with `std::process::Command` like the existing e2e tests rather than `assert_cmd`, which is
not in the workspace and would add a dependency for no gain. `crates/acs-git/tests/hooks.rs`
(installer: fresh, existing hook, husky 9 and 8, pre-commit framework, hooksPath absolute and
relative, `/dev/null`, worktrees, outdated block, non-executable hook, non-shell wrapper, stdin
passing and exit status with a fake `acs`), `crates/acs-git/tests/trailers.rs`,
`crates/acs-cli/tests/git_hooks.rs` (the acceptance scenarios and the pre-push cases).
Test processes run git with `CLAUDECODE` and `GIT_INDEX_FILE` removed, because the suite may itself
run inside Claude Code.

## Consequences

- WP2.5: `acs init` calls `acs_git::hooks::install(&ctx.layout)` and prints the report per hook
  (`Action`); `acs doctor` calls `status` and `install` when `!healthy()`; an `uninstall` path is
  available for `acs off --hooks` or similar. Husky and `pre-commit install` drop the block;
  `doctor` is the repair path. `acs init` should also tell the team the first time it edits a
  committed `.husky/<hook>` (teammates without `acs` get the one-line warning per hook).
- Adding the block to a committed hook file puts it in the adoption commit (`acs/adopt`, WP5.1).
- `claim_conflict`-style wording is duplicated (small `age` and holder formatting in
  `git_hook.rs`) because the engine's helpers are private to `acs-core`, which is frozen.
- Contract change request: none required. (Nice to have in `acs-core`: public message helpers.)
- Untested here: Windows and macOS (the hook scripts use only POSIX `sh` features available in Git
  for Windows; the fake-`acs` and non-shell-wrapper tests are `cfg(unix)`); husky and pre-commit
  were not installed, their layouts are fixtures written from their sources/docs.
- Harness environment detection for Antigravity is unverified; markers are the robust signal.
