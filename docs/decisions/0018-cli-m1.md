# 0018 — CLI for M1: init, status, claim, release, off/on, doctor (WP2.5)

Date: 2026-10-30. Status: accepted (WP2.5), pending orchestrator review.

## Context

WP2.5 adds the human-facing commands of milestone M1 on top of the shared runtime of WP2.1
(`RepoContext`, `seats::current_human_seat`, `status`, `claim_paths`, `release_paths`). Decision 0011
fixed the surface (`acs init|status|claim|release|off|on|doctor`, every command with `--json`);
this record lists the choices made beyond it, the plan and the spec.

## Decision

### Output and errors (all commands)

- `--json` is a per-command flag (a shared `OutputArgs` struct flattened into each command's
  arguments), not a global one: other work packages add variants to `cli.rs` in parallel and
  nothing in `Cli` changes. `acs --json status` is therefore not accepted; `acs status --json` is.
- With `--json` stdout holds exactly one pretty-printed JSON document. `status --json` is the
  `StatusView` serialization unchanged (its field names are the stable contract). The other
  commands print an object with `ok`.
- **Errors.** Human mode: `acs: <message>` on stderr, exit 1. JSON mode: stdout gets
  `{"ok":false,"error":{"code","message"}}`, stderr stays empty, exit 1. Codes: `not_a_repo`,
  `state_unavailable`, `store`, `invalid`, `init_failed`, `cwd`. clap usage errors keep exit 2.
- A **refused claim** is a normal outcome, not an error: exit 1, the engine's message on stderr
  (`Refused (<reason_code>): ...`); with `--json` stdout gets `{"ok":false,"granted":false,
  "reason_code","message"}` (and no error object).
- Human output is wrapped or truncated to 80 columns: paths are cut from the start (the file name
  matters), names from the end, prose is word-wrapped (`commands/support.rs`). Unit and
  integration tests assert it.

### `acs init`

- Writes `config.toml` (`spec = "acs/0.1"` plus commented defaults), and **fully commented**
  `guards.toml` and `territory.toml`. Commented files parse as empty documents, which the loader
  treats as "built-in defaults", so the policy is valid and the effective policy equals having no
  files. The commented guard values are generated from `DEFAULT_SEALED`, `DEFAULT_BAN` and
  `DEFAULT_PROTECTED_BRANCHES`, so they cannot drift; a test uncomments them and checks the
  policy is unchanged. The guards template warns that setting a key replaces its default.
  Files are created with `create_new`, so an existing (or concurrently created) file is never
  overwritten.
- The refspec `+refs/acs/*:refs/remotes/<remote>/acs/*` is added with `git config --add` to
  every remote that has a `url`, only if `git config --get-all remote.<name>.fetch` lacks it.
  No remote: a note, not an error (re-run after adding one). `git` is spawned with the `GIT_DIR`
  family removed.
- Git hooks: one call (`init::hooks::install`), a **stub** until WP2.4's `acs_git::hooks` is
  merged; `doctor` uses `init::hooks::health` the same way. See "Pending" below.
- Harness detection: Claude Code (`claude` on `PATH`, or `.claude/`), Antigravity (`agy` or
  `antigravity` on `PATH`, or `.agents/` or `.agent/`). The exact install commands are printed,
  never run: `claude plugin marketplace add acs-hq/acs` then
  `claude plugin install acs@acs-plugins` (marketplace name from decision 0013; the repository
  slug is the workspace's `repository` URL), and `agy plugin install <acs checkout>/integrations/
  antigravity` (Antigravity has no ACS marketplace; decision 0014). WP5.2's `acs plugin install`
  replaces the text.
- `acs` not on `PATH` is a loud warning in the output and in `warnings` of the JSON, with an extra
  sentence when Antigravity is detected (it denies every tool call). It does not change the exit
  code: `init` itself works without it.
- There are **no prompts, so no `--yes`**: nothing to confirm. WP5.3's proposals add the first
  prompt and the flag.
- Idempotent: a second run leaves policy files and git config byte-identical (tested by comparing
  `.acs/policy/*`, `.git/config` and the hook files before and after); its report says
  `kept`/`present`, and `changed` is false in the JSON.
- `init` does not open the state database or touch `ACS_HOME`; it validates the policy with a
  strict `acs_policy::load` and reports invalid policy as a warning.

### `acs status`

- Uses the human seat (creating it on first use, like `claim`), so "my claims" are the human's.
  Without a usable database there is no seat and the view says why.
- Sealed globs: count plus the first four; `--sealed` lists all (12 globs would otherwise dominate
  the screen). Gate off and an unavailable state database are shown first, with `!!` markers.
  Exit code 0 in all cases.

### `acs claim`, `acs release`

- Human seat, `ClaimOrigin::Human`, through `claim_paths`/`release_paths`: judged exactly like an
  agent's edit (sealed paths, owned zones, other seats' claims). A directory claims its files.
- `release` of a path the seat does not hold is **not** an error (idempotent: "not held, left
  alone"); a path outside the repository is (exit 1). `release --all` releases the human seat's
  claims directly through the store (so symbol claims go too) and conflicts with explicit paths.

### `acs off`, `acs on`

- Set and clear `FLAG_GATE_OFF` in the repository's `state.db`. Both are idempotent and say
  whether anything changed. `off` says sealed paths still hold and that `acs status` shows it.
  Both live in `commands/off.rs`.

### `acs doctor`

- One pass/warn/fail line per check; `--fix` repairs; exit 1 when any check **fails** (warnings
  never fail). `--json`: `{"ok","fix","checks":[{id,title,status,message,fixed,hint}],"summary"}`.
- Checks: `acs_home` (exists or "created on first use"; on Unix, no group/other bits on `ACS_HOME`,
  `repos/`, `index/`, the repository directory and its subdirectories, `state.db` and its `-wal`
  and `-shm`; a Windows note about inherited ACLs per decision 0003), `repo_id`, `state_db`
  (opens without creating it, schema current, `integrity_check`), `policy`, `policy_cache`,
  `git_hooks`, `acs_on_path`, one `plugin_<harness>` per detected harness, `gate`. Outside a git
  work tree only `acs_home`, `acs_on_path` and a `repository` warning run.
- Fixes: tighten permissions (never loosen, never change owner); **move a corrupt `state.db` aside**
  as `state.db.corrupt-<unix seconds>` (with `-wal` and `-shm`), create a new one and verify it:
  seats and claims are reset, snapshots and the old file are kept; delete an unreadable
  `cache/policy.json` (the next call rebuilds it); install hooks .
  Corruption is the only database failure that is fixed; a newer schema, a lock or a permission
  error are reported with a hint.
- An **invalid policy file is a warning**, not a failure: the engine keeps enforcing the last valid
  policy or the built-in defaults (SPEC section 11), the error is shown in full, and the exit code
  stays 0. No `.acs/policy/` is also a warning ("run `acs init`").
- **Policy cache** validity is checked structurally (the JSON has the fields `acs-policy` writes);
  an entry from another build or older than the files is fine, it is refreshed on the next load.
- **`acs` on `PATH`** is a **failure** when a harness plugin is confirmed installed (its hooks would
  run without the binary: Antigravity denies everything, Claude Code runs tools unchecked) and a
  warning otherwise (a machine that only uses the CLI).
- **Plugin installed?** Best effort without running any harness: Claude Code's
  `enabledPlugins["acs@acs-plugins"] == true` in the project, local or user settings file
  (`$CLAUDE_CONFIG_DIR` or `~/.claude`); Antigravity's `<work tree>/.agents/plugins/acs`,
  `.agent/plugins/acs` or `~/.gemini/config/plugins/acs`. Not found is a **warning** with the install
  command ("not confirmed": another scope, managed settings or an internal registry may hold it).
  Nothing is spawned (`claude plugin list`, `agy plugin list` formats are not specified).
- The gate being off is a warning with the `acs on` hint; `--fix` never turns the gate on.

### Git hooks (WP2.4's installer)

`init::hooks::install` and `init::hooks::health` are the only calls into `acs_git::hooks`
(`install`, `status`; decision 0015). `init` prints one line per hook (`created`, `injected`,
`wrapped`, `updated`, `unchanged`); a second run reports all `unchanged`. With husky 9 it adds a
note that ACS edited the committed `.husky/<hook>` files. `core.hooksPath=/dev/null`
(`HooksError::Disabled`) is a warning, not a failure: the person turned hooks off. `doctor` lists
per hook why `status().healthy()` is false (block missing, outdated, not executable), mentions that
husky and `pre-commit install` drop the block, **fails** (missing hooks weaken the backstop) and
`--fix` runs `install` again and re-checks. An unreadable or disabled hook setup is a warning.

## Consequences

- `cli.rs` gains seven variants and match arms; the existing unit tests that destructured
  `Command::Hook` with an irrefutable `let` now use `let ... else` (any new variant breaks them).
- `commands/mod.rs` gains `claim`, `doctor`, `init`, `off`, `release`, `status` and a private
  `support` module (shared formatting, `PATH` lookup, error type) beyond the "one line each".
- No new dependencies. `assert_cmd` was not used (not vendored offline); the tests drive the built
  binary with `std::process::Command`, as the existing e2e tests do.
- The human claim of a file an agent later wants makes the agent's denial name the human
  (`harness: human`); `acs release` is how they hand it back.
