# 0056 — `v1.0.0` is tagged for the first testers

Date: 2026-11-23. Status: accepted.

Decided by: the human, that `v1.0.0` is tagged now because the first testers download and try ACS
on 2026-11-24 (in the session of issue 79). Claude for how: the README and the setup skill install
from the release again, and what was not run before the tag is listed here.

## Context

The updater's real run passed on Windows (`docs/releases/v1.0.0-updater.md`): `v1.0.0-rc.2`
installed with the PowerShell installer replaced itself with `v1.0.0-rc.3`. Decision 0051 had the
README and the setup skill build `acs` from `main` until the first release, because no installer
link worked. `docs/releases/README.md` asks for the manual check of plan section 9.1 before a
release, and decision 0019 says that until the Antigravity gate passes ACS is proven only across
Claude Code sessions.

## Decision

1. **The workspace version is `1.0.0`**, and the human's request is the go-ahead to tag and push
   `v1.0.0` from `main`.
2. **The README and the setup skill (all three copies) install from the latest release again:**
   `irm .../releases/latest/download/acs-cli-installer.ps1 | iex` on Windows, the shell installer on
   macOS and Linux, Scoop from the release's `acs.json`. Building from `main` stays as the fallback,
   and the setup skill uses it only when the pilot asks. Decision 0051 ends here.
3. **Not run for this tag:** the plan section 9.1 manual check with real Claude Code sessions (last
   recorded for v0.1.0 in `docs/releases/v0.1.0.md`), and the Antigravity gate's remaining desktop
   app checks (issue 6). macOS and Linux installs were tried only by the release's `Installers`
   jobs, not by a person.

## Consequences

- Testers on Windows who use the PowerShell installer get later 1.x releases by themselves; the
  next release must be signed with the same key.
- The `Installers` job `acs plugin install, real Claude Code` fails on Linux (issue 84). It does
  not block the release, which is published before that job runs.
