# 0029 Lore: injection, staleness and proposals (Phase 6)

Date: 2026-11-09. Work packages WP6.1 and WP6.2.

## Context

The plan asks for lore entries (`.acs/policy/lore/**/*.md`, SPEC section 5.4) to be shown to an
agent "on the first claim in a scope, once per session, within a cap", marked when stale, and for
agents to propose lore that an owner reviews and commits on `acs/lore-<id>`. The engine is pure
(no I/O), lore needs file and git reads, and the hook budget is tight (plan section 4.7).

## Decision

1. **Injection lives in the pipeline, not the engine.** `runtime::lore` runs after the engine
   decided, for any outcome but `deny`, and puts its blocks in front of the notices in
   `decision.context` (SPEC section 9, step 7). The engine's seam comment now says so. Conformance
   fixtures that need lore will drive the binary, which they do anyway.
2. **"Entering a scope" is any tool call on a path in it, reads included, plus `acs_claim`.**
   Agents read before they edit, so lore that arrives with the first read is there when the edit
   is planned; waiting for the first claim would deliver it after the edit was written. Reads are
   not in `Normalized` (the gate only needs writes), so read paths, and the literal read targets of
   shell commands, are resolved only when `.acs/policy/lore/` exists: repositories without lore
   pay one `stat` per pre-tool call.
3. **Once per seat, decided by the database.** Migration 0006 adds `lore_loaded (seat_id,
   lore_id, loaded_at, stale)` with that primary key. `mark_lore_loaded` inserts with `OR IGNORE`
   and returns only the rows it inserted; only those are shown, so two racing hooks of one seat
   never show an entry twice. A seat is one harness session. WP4.1 fills
   `SessionRecord.lore_loaded` from `lore_loaded_for_seat`.
4. **The cap is per call, in characters.** `[lore] max_inject_chars` (default 4000) and
   `[lore] stale_percent` (default 30) are new optional keys of `config.toml` (`LoreConfig`, a
   contract change to `Config`; schema regenerated). Entries go most specific first (the zone
   ranking of `acs-policy`, now public as `Glob::match_specificity`); what does not fit is not
   marked as shown and comes with the next call in the scope, with a one-line note saying so. When
   not even the first entry fits, its body is cut and the block names the file.
5. **Staleness is measured against `HEAD`, not the work tree, and cached per `HEAD`.** Changed
   lines (added plus deleted, `git diff --numstat --no-renames`) between `written_against` and
   `HEAD` over the lines the scope had at `written_against`, on text files the scope's globs match
   in the spec's own dialect (git pathspecs only narrow what git reads; `{a,b}` globs fall back to
   their literal directory). Ignoring uncommitted work keeps the answer a function of `HEAD`, so
   `cache/lore-stale.json` holds it and hooks measure each entry once per commit, not once per
   session. A `written_against` this clone lacks counts as stale. Stale entries are still shown,
   with a request to verify them; no `lore_stale` notice is generated (the marker on the entry
   itself reaches the agent at the moment it matters).
6. **Proposals are local files; review commits on a branch with plumbing.** `acs_lore_propose`
   stores a JSON file in `ACS_HOME/repos/<id>/pending/lore/` after checks (text at most 4000
   characters, at most 16 valid globs, `replaces` must name an entry, at most 200 waiting).
   `acs lore review` (interactive, or `--list`, `--accept <id> [--body-file] [--owner]`,
   `--reject <id>`) writes the entry with a temporary index, `commit-tree` and `update-ref` onto
   `acs/lore-<id without lore_>`, on top of that branch if it exists, else `HEAD`. The work tree,
   the index and the checked-out branch are never touched. The user's own identity and signing
   configuration are used. The owner written in is the replaced entry's owner, else the owners of
   the zone the scope's literal start falls in, else the reviewer; a reviewer who is not the owner
   is told so but not stopped (CODEOWNERS on the merge is the real gate).
7. **Agents may read lore from the CLI, never review it.** Self-protection allows `acs lore list`,
   `acs lore show`, `acs lore stale` and help, and denies every other `acs lore` action with a
   message that points to `acs_lore_propose`. `.acs/**` stays sealed, so agents cannot write lore
   by any file route either.

## Consequences

- The state schema is now version 6. After this merges, the human reinstalls `acs`; older builds
  report the state unavailable once a newer build has migrated it (handoff section 2, WP7).
- The first touch of a scope with lore costs two `git diff` runs per entry on a new `HEAD`
  (cached afterwards), on top of the pre-tool budget. In a repository with lore, every pre-tool
  call also walks and parses `.acs/policy/lore/` (no compiled cache yet, unlike the policy files).
  Neither is benchmarked; WP10.1 should add a lore case to `benches/hook_paths.rs`, and a cache
  keyed by the lore files' hash is the obvious fix if it misses.
- After `/clear` or a compaction the agent loses lore it was shown, and the seat still counts it
  as shown. Resetting `lore_loaded` on a `session_start` whose source is `clear` or `compact`
  needs the adapter to pass the source through; left for later.
- Lore text is the owners' own words, injected verbatim into agents' context: a malicious lore
  entry is a prompt-injection vector, mitigated only by review of `.acs/policy/` changes
  (CODEOWNERS). WP10.3's threat model must cover it ("poisoned lore").
- `acs lore review --accept` can be scripted. Agents are stopped by self-protection; an agent
  whose shell ACS cannot see could still run it, but the result is only a branch that a person
  must merge.
- WP5.4 (instruction-file import) builds on `acs_lore::format` (`LoreEntry::parse`,
  `format::render_file`) and `propose::file_for` for file placement.
