# 0007: Path safety

Date: 2026-10-29 (WP1.3)

## Context

Every gate decision starts with "which file is this, really?". Agents write `../x`, `a/link/../b`, absolute paths through symlinks and Windows junctions, and paths in the wrong case on case-insensitive filesystems. The incident behind this work package is a recursive delete aimed at a scratch copy that contained junctions into the live tree: the target looked harmless and the delete reached 48,000 live files. `acs-paths` produces the `ResolvedPath`, `PathLocation` and `Expansion` values defined in `acs_core::gate` (decision 0004, rules 5 and 6).

## Decision

**Walk, do not canonicalize.** `PathResolver::resolve` walks the path one component at a time with `lstat`, following each symlink or junction by hand and applying `..` to the already-resolved prefix, so `a/link/../b` follows the link first. `std::fs::canonicalize` is only used for things that exist: the root, link targets (to classify them) and, on Windows, the existing prefix at the end (the OS then supplies the on-disk case and expands 8.3 names). A missing component ends the walk and the remainder is appended lexically, so new files and directories resolve to where they would be created. A dangling link resolves to where a write through it would land. More than 40 link hops is `Unresolvable` ("a link loop").

**Hot path.** The root is canonical, so a path spelled under it (compared component-wise, ignoring case when the filesystem does) starts the walk at the root and costs one `lstat` per component below it: about 3 microseconds for `src/deep/c.rs` in a release build (three `lstat`s), against about 5 microseconds to construct the resolver (canonicalize root, probe case, look at `.git`). Paths that are not spelled under the root walk from the filesystem root.

**Two resolutions.** `resolve` follows every link, including the last component (what a write or read does). `resolve_entry` leaves a link in the last component alone unless the path ends with a separator (what `rm` and `mv` see): deleting a symlink inside the repo that points outside is an in-repo delete of the link, not of its target. The pipeline picks per operation; nothing in the contract forces either.

**`via_link`.** True when the walk followed a link, except links that merely name an ancestor of the repository root (`/var` -> `/private/var` on macOS, a symlinked home). Those are where the repository lives, not a way into or out of it; counting them would flag every path on such machines. A link whose target is the root itself, or any link inside the root, counts.

**The repository root as a path.** `RepoPath` cannot be empty, so the root itself is `InRepo(".")`, and `linked_into_repo` contains `"."` when a link reaches the whole tree. A policy glob will not match `"."`; the expansion lists the files, which is what the engine checks. Consumers must not treat `"."` as a file.

**`.git`.** A normal `.git` is inside the root and needs no mapping. For linked worktrees and submodules (`.git` is a file) and for a `.git` symlink to elsewhere, the resolver finds the real git directory (and `commondir`) and reports paths inside them as `.git/...`, so sealed globs for `.git/**` catch hooks and config wherever they live. The git directory of the main working tree seen from a linked worktree is the common dir; other working trees are outside.

**Case.** Case-insensitivity is probed once per resolver: stat the root's name with its ASCII case swapped and compare device and inode (Unix) or canonical paths (Windows). The result is exposed (`case_insensitive()`) for compiling the policy and can be overridden (`with_case_insensitive`) for tests. When insensitive: the root prefix matches ignoring case; on Windows the final canonicalization gives the on-disk case; elsewhere (macOS, case-insensitive Linux mounts) each existing component is looked up in its parent's directory listing to get its on-disk spelling. That costs a directory read per component, only on those filesystems, and stops at the first exact match. Components that do not exist keep the spelling given. Unicode normalization differences (NFC/NFD on macOS) are not handled; names are compared by lowercase only.

**Windows spellings.** `\\?\C:\...` and `\\?\UNC\...` are rewritten to the ordinary form on input and on every canonicalization result (long paths work without the prefix through `std`), so one spelling is compared. `/` and `\` mix freely; drive-letter case is ignored; `\dir` and `C:dir` take the drive and directory of `cwd` (another drive is `Unresolvable`); trailing dots and spaces and `:stream` suffixes are dropped from components (Win32 treats them as the same file); reserved device names (`NUL`, `COM1`, ...) are `Outside("\\.\NAME")`. Junction targets read as `\??\C:\x` are cleaned. A UNC path to the local machine's administrative share is a network path and resolves `Outside`: that is the safe direction (the engine asks) rather than a way around a sealed glob.

**Recursive reach.** `resolve_recursive(raw, cwd, cap)` resolves a directory (following links, conservatively) and walks the subtree without following links, resolving every link it meets and recording those that land in the repository outside the walked subtree (a link back into its own directory adds nothing; nested targets are kept individually in `linked_into_repo`). The walk is bounded by `cap` directory entries; `resolve_recursive_report` also says whether it was cut short, and the pipeline should treat truncation as "may reach more". `expand_recursive(&ResolvedPath, cap)` lists repository files: the subtree if it is in the repository (a link is one entry), plus the files under each `linked_into_repo` path (and under links found in an in-repo subtree), one hop only. For a directory outside the repository only the `linked_into_repo` paths are listed, so pass the output of `resolve_recursive`. Nested link targets collapse to the outermost. Hidden files and `.git` are included: `rm -r` deletes them.

**Globs.** `expand_glob(pattern, cwd, recursive, cap)` expands with shell semantics, matching one segment at a time with `globset` (`*`, `?`, `[..]`, `[!..]`; no `/` crossing; no leading-dot match unless the segment starts with a dot). `**` as a whole segment is treated as globstar (zero or more directories; last, everything beneath), which over-approximates bash without `globstar` in the safe direction. An invalid segment such as an unterminated `[` is literal, like the shell. `.gitignore` is never read. With `recursive`, a matched directory contributes its files; without, directories are skipped. A trailing separator means directories only. A plain path is a glob with no metacharacters, so `expand_glob` also serves as the general `expand`. The scan has a budget proportional to `cap`; hitting it or `cap` sets `truncated`.

## Consequences

- Dependencies added: `globset` (default features off), alongside the existing `dunce`. Its transitive crates (`aho-corasick`, `regex-automata`, `bstr`, `memchr`) are permissively licensed.
- The Windows-only behavior (junction detection through `FileType::is_symlink`, canonicalization case, `\\?\` handling, drive-relative paths, device names) is covered by `#[cfg(windows)]` tests and the cross-platform junction tests that use `mklink /J`; they run on CI's Windows runner. They could not be run while writing this code.
- Symlinks and junctions are the only links handled. Other reparse points (OneDrive placeholders, WSL, mount points to other volumes that are not name surrogates) are treated as ordinary directories. Hard links to files inside the repository from outside it are not detectable by path and are out of scope.
- A time-of-check/time-of-use gap exists by nature: a link can be created between resolution and the tool running. The post-tool change attribution (WP2.1) is the backstop.
- `Outside` carries a lossy UTF-8 rendering of the canonical path, and `RepoPath` components are lossy too; non-UTF-8 file names cannot round-trip.
